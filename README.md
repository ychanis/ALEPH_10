# 과제 10 | AI와 함께 쓰는 첫 논문

## 로그인 실패 후 일시 차단 정책의 효과와 정상 사용자 차단

**작성자: 영찬 · 작성일: 2026-10-23**  
**관심 분야: 정보보안, 로그인 보호, 보안 정책 운영**

로그인 실패가 반복되면 계정을 잠그는 정책은 공격을 얼마나 제한할까? 같은 계정의 정상 사용자에게는 어떤 영향을 줄까?
이 프로젝트는 이 두 질문을 동일한 요청 자료로 비교한 사건 기반 모의실험이다. AI와 가설을 정리하고, 합성 요청을 생성해 두 정책에 적용한 뒤 결과·한계·재현 방법을 논문으로 정리했다.

기존 과제의 코드와 원자료를 합치지 않은 독립 프로젝트다. 실제 사이트나 계정에 로그인 요청을 보내지 않았으며, 실제 사용자의 비밀번호나 유출 자료도 사용하지 않았다.

## 2. 연구 질문과 가설

**연구 질문:** 동일한 로그인 요청에 실패 후 일시 차단 정책을 적용하면 비밀번호 추측 검사 횟수와 정상 접근은 어떻게 달라지는가?

> 동일한 로그인 요청 자료에서 5회 연속 실패 후 30초 동안 계정을 차단하면, 차단하지 않을 때보다 600초 동안 실제 검사되는 공격 요청 수가 줄어든다.

‘실제 검사’는 차단을 통과해 비밀번호 정오 판정까지 진행되는 것을 뜻한다. 차단된 요청은 검사 횟수에 포함하지 않는다. 공격 요청은 모두 오답으로 지정했으므로 이 연구는 **공격 성공률이 아니라 검사 기회 제한 효과**를 측정한다.

사전 지정한 시나리오 중 평균 검사 횟수가 줄지 않는 조건이 있다면, 모든 조건에서 감소한다는 해석은 지지되지 않는다. 가설과 반대되는 결과도 삭제하지 않는 것을 원칙으로 했다.

## 3. 후보를 좁힌 이유

| 후보 주제 | 선택 또는 제외 이유 |
| --- | --- |
| 방화벽 규칙 수와 응답시간 | GNS3 부팅 부담과 병행 작업 때문에 제외 |
| 방화벽 로그 기록과 처리 성능 | 가상 장비 및 동일 트래픽 환경 구성이 필요해 제외 |
| 비밀번호 길이와 추측 성공률 | 비밀번호 분포 가정에 결과가 크게 좌우되어 이번 핵심 주제에서 제외 |
| 로그인 실패 후 일시 차단 | 가상머신 없이 재현 가능하고, 보호 효과와 정상 접근 손실을 함께 볼 수 있어 선택 |

논문에는 확장한 질문 10개, AI와 주제를 좁힌 과정, 실제 사용자 선택과 AI가 정한 설계를 구분해 적었다.

## 4. 실험 설계

| 항목 | 설정 |
| --- | --- |
| 비교 정책 | 차단 없음 / 5회 연속 실패 후 30초 계정 차단 |
| 공격 간격 | 빠름 0.5초 / 중간 2초 / 느림 10초 |
| 간격 변동 | 매 간격에 0.8~1.2배 균등 변동 |
| 관찰 범위 | 반복당 가상 시간 0초 이상 600초 미만 |
| 반복 | 각 공격 조건 30쌍, 총 90쌍·180회 정책 실행 |
| 정상 요청 | 반복당 20건, 오입력 확률 10%로 합성 |
| 공격 요청 | 같은 계정에 대한 오답 요청만 생성 |
| 상태 초기화 | 정상 로그인 성공 또는 차단 만료 후 실패 횟수 초기화 |
| 차단 중 요청 | 검사하지 않으며 차단 시간을 연장하지 않음 |
| 난수 시드 | 2026102301~2026102330 |

각 쌍에는 **완전히 같은 요청 자료**를 입력했다. 공격 간격이 달라도 정상 요청은 같게 유지했다. 실제 10분을 기다리는 방식이 아니라 가상 시각 순서대로 상태를 계산하므로 가상머신과 네트워크 장비 없이 실행할 수 있다.

`design.json`에 설계를 확정하고, 최초 실행 전에 `design_record.json`에 코드와 설계의 SHA-256을 기록했다. 로컬 선행 기록이며 외부 기관의 사전 등록은 아니다. 실행 후 설계와 가설은 바꾸지 않았다.

## 5. 주요 결과

| 공격 조건 | 차단 없음: 평균 공격 검사 | 차단 적용: 평균 공격 검사 | 평균 감소율 | 정상 요청 차단 |
| --- | ---: | ---: | ---: | ---: |
| 빠름 | 1,199.07건 | 98.17건 | 91.81% | 553/600건 (92.17%) |
| 중간 | 299.27건 | 85.87건 | 71.30% | 443/600건 (73.83%) |
| 느림 | 59.43건 | 47.60건 | 19.90% | 162/600건 (27.00%) |

공격 검사 건수는 반복당 평균이며, 정상 차단 건수는 조건별 30회 합계다. 감소율은 각 반복의 감소율을 계산한 뒤 평균했으므로 표시된 평균 건수로 다시 계산한 값과 소수점에서 다를 수 있다.

세 조건에서 모두 검사 횟수가 줄어 가설을 지지했다. 그러나 빠른 공격에서는 정상 요청도 대부분 차단됐다. 올바른 비밀번호가 입력된 정상 요청 542건 중 497건까지 막혔다. 따라서 이 결과는 ‘일시 차단이 언제나 좋은 정책’ 또는 ‘공격만 선택적으로 차단한다’는 주장을 뒷받침하지 않는다.

차단은 검사를 건너뛰도록 구현되어 있어 감소 방향 자체는 상당 부분 예상된다. 여기서 확인한 것은 설정한 조건에서의 **감소 폭과 정상 접근 손실**이다. 요청 생성은 계속되므로 네트워크 트래픽이나 공격자의 시도 자체가 줄었다는 뜻도 아니다.

## 6. 작성자의 판단과 후속 적용 제안

작성자는 **사전 접근 규칙과 사후 이상 징후 분석을 상호 보완적으로 연결해야 한다**고 판단했다. 사전 규칙을 통과하지 못한 접근은 인입 단계에서 차단하고, 정상적으로 통과한 접근도 이후 행위를 계속 관찰해 이상 징후가 확인되면 방화벽 차단으로 연결하는 방식이다.

이 제안은 본 실험을 바탕으로 작성자가 제시한 운영 방향이다. 결합 정책이 단일 정책보다 가장 효과적이라는 점, 실시간 탐지 정확도, 방화벽 차단 속도는 이번 실험으로 검증하지 않았다.

### 현재 파일의 역할과 제안의 차이

| 구분 | 현재 패키지에서 하는 일 | 후속 시스템에서 필요한 것 |
| --- | --- | --- |
| `checklist.md` | 과제 제출 기준과 근거 위치를 정리한 문서 | 프로그램이 읽고 요청 허용 여부를 판단할 수 있는 접근 정책 |
| `results/summary.json` | 실험 종료 후 조건별 평균·합계를 담는 집계 파일 | 개체별 사건 기록과 지속적인 이상 징후 분석 |
| 차단 기능 | 가상 시간 안에서 계정 잠금 상태를 계산 | 실제 탐지 결과를 전달하는 방화벽 연동 및 차단·해제 절차 |

따라서 현재 두 파일이 실시간으로 연동되거나 실제 방화벽을 제어하는 것은 아니다. 후속 연구에서는 탐지 정확도, 정상 요청 차단율, 탐지부터 차단까지 걸린 시간, 잘못된 차단의 해제 가능성을 함께 비교할 수 있다.

## 7. 실행과 재현

### 필요한 환경

- Python 3.9 이상
- 별도 패키지 설치 없음: Python 표준 라이브러리만 사용
- 외부 API, 계정, 인증 키, 인터넷 연결, 가상머신 불필요

ZIP을 풀고 **`run.py`와 `design.json`이 있는 `ALEPH_10` 폴더**에서 터미널을 연다.

### 저장된 원자료로 결과 다시 계산

```bash
python run.py --replay
```

Windows에서 `python`이 인식되지 않으면 다음 명령을 사용한다.

```bash
py -3 run.py --replay
```

이 명령은 원자료를 읽어 `results/events.csv`, `results/runs.csv`, `results/summary.json`을 다시 계산한다. 기존 결과 파일을 갱신하므로 원본을 보존하려면 ZIP을 별도 폴더에 풀어 실행한다.

### 원자료까지 같은 시드로 다시 생성

```bash
python run.py
```

이 명령은 `data/requests.csv`도 재생성한다. 재현을 확인할 때는 먼저 수정하지 않은 원본으로 실행한다. 설계를 바꾸는 추가 실험은 별도 복사본에서 진행한다.

### 한 번에 검증

```bash
python verify.py
```

정상 출력:

```text
PASS: hashes, isolated replay, row counts, lock threshold/expiry/success reset
```

검증기는 다음을 확인한다.

1. 제출 파일의 SHA-256이 해시 목록과 일치하는지 확인한다.
2. 임시 폴더에 복사하고 저장된 원자료를 재분석한다.
3. 재분석한 요청별·반복별·요약 결과가 원본과 바이트 단위로 일치하는지 확인한다.
4. 원자료 48,533행과 정책별 판정 97,066행을 확인한다.
5. 5번째 실패, 차단 해제 시각, 성공 후 실패 횟수 초기화 경계를 확인한다.

파일을 직접 수정하면 해시 불일치가 발생할 수 있다. 이때는 제출 ZIP의 원본과 수정 실험 폴더를 구분해서 확인한다.

## 8. 자료 구성과 추적 방법

| 경로 | 내용 |
| --- | --- |
| `design.json` | 가설, 표본, 정책, 시드, 측정값과 고정 조건 |
| `design_record.json` | 최초 실행 전 설계·코드 해시와 기록 시각 |
| `run.py` | 합성 입력 생성, 두 정책 평가, 요약 계산 |
| `verify.py` | 독립 폴더 재현, 원자료 행수, 무결성 및 상태 경계 검증 |
| `data/requests.csv` | 합성 입력 원자료 48,533행 |
| `results/events.csv` | 정책별 요청 판정 97,066행 |
| `results/runs.csv` | 조건·반복·정책별 집계 180행 |
| `results/summary.json` | 세 조건별 최종 요약 |
| `results/execution.txt` | 최초 전체 실행 출력 |
| `data_counts.json` | 전체 및 조건별 원자료 행수 |
| `execution_metadata.json` | 실행 환경과 기록 시각 |
| `SHA256SUMS.json` | 최종 파일의 SHA-256, 해시 목록 자체는 제외 |

개별 요청을 찾을 때는 `scenario`, `rep`, `id`를 함께 사용한다. `events.csv`에서는 `policy`를 추가로 구분한다. `outcome`은 `failure`, `success`, `blocked` 중 하나이며, `failure_count`와 `locked_until`로 당시 계정 상태를 확인할 수 있다.

## 10. 연구의 한계와 수행 구분

- 모든 사용자 행동은 합성 자료다. 사람을 대상으로 수집한 자료가 아니다.
- 공격은 모두 실패하므로 계정 탈취 확률이나 공격 성공률을 평가하지 않는다.
- 단일 계정 모형으로, 다중 계정·분산 IP·다중 인증·실제 서비스 복구 흐름은 포함하지 않는다.
- 실제 지연, CPU 부하, 해시 비용, 네트워크 성능을 측정하지 않았다.
- 30회 반복은 모형의 입력 변동을 보여 주며 현실 전체에 대한 일반화를 보장하지 않는다.
- 사전 규칙과 사후 탐지의 실시간 연동 및 방화벽 제어는 후속 제안이다.
- 주제 선택과 운영 방향 판단은 작성자가 했고, 세부 설계·코드 실행·분석·원고 작성은 AI가 수행했다. 사용자 PC에서 직접 실행했다고 기록하지 않았다.
- 과제의 계획시간 8~10시간을 실제 수행시간으로 주장하지 않았다.

**결론:** 일시 차단 정책은 설정한 모형에서 공격 검사 기회를 줄였지만 정상 접근에도 큰 손실을 만들었다. 보호 효과와 정상 접근 영향을 함께 평가해야 하며, 작성자가 제안한 사전·사후 결합 정책의 효과는 별도 실험으로 확인해야 한다.
